Déployer Takussan de A à Z

Frontend Next.js sur Vercel. Backend Laravel sur VPS Contabo via deploy.sh orchestré depuis GitHub Actions. Ce guide te fait passer d'un VPS vierge à une preview + prod opérationnelles, en t'expliquant chaque étape.

0Vue d'ensemble

À qui s'adresse ce guide ? À toute personne qui doit déployer Takussan en preview ou en prod, même sans expérience préalable d'un VPS. Chaque section commence par un Pourquoi, chaque commande est accompagnée d'un commentaire en français, et des encadrés Si ça échoue… couvrent les pièges classiques.

Ce que tu vas obtenir à la fin

  • Un site Next.js public en preview (preview.takussan.com) et en prod (takussan.com) servis par Vercel.
  • Une API Laravel publique sur le même VPS Contabo, isolée par environnement : preview.api.takussan.com et api.takussan.com.
  • Des déploiements automatisés à chaque push : push preview → preview API redéployée ; push master → prod API redéployée. Vercel gère le front de son côté.
  • Un rollback automatique si un deploy casse (symlink atomique).

Prérequis

  • Un compte GitHub avec accès au repo takussan en owner ou collaborateur (besoin d'ajouter des secrets).
  • Un compte Vercel connecté à GitHub.
  • Un compte Cloudflare avec la zone DNS takussan.com.
  • Un accès SSH admin (sudo) au VPS Contabo (l'IP + un user qui peut faire sudo).
  • Un client local : git, ssh, scp, curl, php 8.3+.

Glossaire — vocabulaire que tu vas rencontrer

VPS
Virtual Private Server. Une machine Linux à toi, ici chez Contabo, accessible en SSH.
vhost
Virtual Host. Un fichier de config Nginx qui dit "le trafic pour tel domaine doit aller vers telle app".
PHP-FPM
FastCGI Process Manager. Le service qui exécute le code PHP appelé par Nginx via un socket.
opcache
Cache PHP qui garde le bytecode compilé en RAM. Doit être reloadé après chaque deploy.
deploy key
Clé SSH read-only liée à un seul repo GitHub. Permet au VPS de cloner sans password.
symlink swap
Bascule atomique entre deux versions du code via un lien symbolique current renommé d'un coup.
DNS only (gray cloud)
Mode Cloudflare où CF ne proxifie pas — le trafic va directement au VPS. Indispensable pour Vercel et pour Certbot.
Sanctum
Le système d'authentification Laravel à base de cookies SPA, utilisé entre le front Vercel et l'API Contabo.
sudoers
Fichier /etc/sudoers.d/... qui autorise un user à exécuter certaines commandes sans password.
certbot
Outil qui obtient et renouvelle gratuitement les certificats SSL Let's Encrypt pour Nginx.

Ordre de lecture recommandé : suis les sections dans l'ordre. Le sommaire à gauche reflète l'enchaînement réel des étapes. Chaque section te dit clairement quand elle s'applique à preview, à prod, ou aux deux.

2DNS Cloudflare

Pourquoi cette étape ? Pour que tes domaines pointent vers les bons serveurs : Vercel pour le front, ton VPS Contabo pour l'API. Sans ces DNS records, rien ne marche.

Connecte-toi à dash.cloudflare.com → zone takussan.com → DNS → Records. Tu vas créer 4 records, deux pour le front Vercel et deux pour l'API VPS.

TypeNomValeurMode CFPour
CNAME@ ou wwwcname.vercel-dns.comDNS only (gris)Front Vercel prod
CNAMEpreviewcname.vercel-dns.comDNS only (gris)Front Vercel preview
Aapi<IP_VPS>DNS only (gris)API VPS prod
Apreview.api<IP_VPS>DNS only (gris)API VPS preview

Le mode "DNS only" (nuage gris) est obligatoire, pour deux raisons :

  • Vercel : ne jamais proxifier via Cloudflare. Sinon double-CDN, conflits TLS, et Vercel ne reçoit pas la vraie IP visiteur.
  • API VPS : Certbot Let's Encrypt fonctionne directement, sans gymnastique TLS. Si tu passes en "Proxied" plus tard, tu devras ajuster TRUSTED_PROXIES (CIDR Cloudflare) et basculer SSL CF en "Full (strict)".

2.1 Vérifier que les DNS sont propagés

Depuis ton poste local, dans un terminal :

bash 
# Doit retourner l'IP du VPS pour les sous-domaines API
dig +short api.takussan.com
dig +short preview.api.takussan.com

# Doit retourner une IP Vercel pour les sous-domaines front
dig +short takussan.com
dig +short preview.takussan.com

Si dig ne retourne rien…

  • Attends quelques minutes — la propagation peut prendre 1 à 10 min.
  • Vérifie que le record est bien créé dans Cloudflare et que le nuage est gris.
  • Force un refresh : dig @1.1.1.1 +short api.takussan.com (passe par les DNS Cloudflare directement).

3Frontend sur Vercel

Pourquoi Vercel ? Vercel build et sert le frontend Next.js automatiquement à chaque push GitHub. Pas de serveur à gérer, pas de build à orchestrer côté VPS — Vercel le fait pour toi. C'est l'option la plus simple pour Next.js.

3.1 Importer le repo

  1. Va sur vercel.com/new → GitHub → choisis le repo takussan.
  2. Dans Root Directory, sélectionne takussan-web (c'est là que vit le code Next.js dans le monorepo).
  3. Framework Preset : Next.js (détecté automatiquement).
  4. Configure les variables d'environnement ci-dessous AVANT de cliquer Deploy, sinon le premier build sera cassé.

3.2 Variables d'environnement Vercel

Audit du code (grep "process.env" takussan-web/src/) : seule NEXT_PUBLIC_API_URL est utilisée. Pas besoin d'en déclarer d'autre.

VariableProductionPreviewDevelopment
NEXT_PUBLIC_API_URLhttps://api.takussan.comhttps://preview.api.takussan.comhttp://localhost:8002

Vercel injecte automatiquement VERCEL_ENV, VERCEL_URL, VERCEL_GIT_COMMIT_* et autres — accessibles côté serveur uniquement. Si tu as besoin d'un jour distinguer preview/prod dans le code, lis process.env.VERCEL_ENV dans un Server Component plutôt que de dupliquer en NEXT_PUBLIC_*.

3.3 Branche de production + domaines custom

  1. Settings → Git → Production Branch : master.
  2. Settings → Domains :
    • Ajoute takussan.com (et/ou www.takussan.com) → laisse sur Production (= branche master).
    • Ajoute preview.takussan.com → Edit → Git Branch = preview.

Vercel utilise les enregistrements DNS configurés au §2 (cname.vercel-dns.com) pour valider et émettre les certificats TLS automatiquement. Aucune action côté Contabo pour ces domaines.

3.4 Configurer next.config.ts pour les images de l'API

Next.js refuse par défaut de servir les images dont le hostname n'est pas autorisé. Comme l'API héberge les médias (avatars, photos de propriétés…), il faut whitelister ses domaines.

typescript — takussan-web/next.config.ts 
const nextConfig = {
  images: {
    remotePatterns: [
      { protocol: 'https', hostname: 'api.takussan.com' },
      { protocol: 'https', hostname: 'preview.api.takussan.com' },
    ],
  },
};
export default nextConfig;

4Audit du VPS — prérequis

Pourquoi cette étape ? Le VPS Contabo héberge déjà CheckPrint. On vérifie ce qui est en place pour éviter de réinstaller ou d'écraser des configs. Le script server-setup.sh (§5) suppose que la baseline Linux est OK.

Connecte-toi en SSH avec un user admin (pas deploy), puis exécute les vérifications :

bash — sur le VPS 
# 1. L'infra CheckPrint est-elle là ?
ls -la /var/www/
#   → tu dois voir check-print-plus/ et check-print-plus-preview/

# 2. Le user `deploy` existe ?
id deploy
#   → uid=... groups=...,www-data

# 3. Pools PHP-FPM déjà présents (à ne pas écraser)
ls /etc/php/*/fpm/pool.d/

# 4. Vhosts nginx déjà présents
ls /etc/nginx/sites-enabled/

# 5. Services queue déjà actifs
sudo systemctl list-units 'checkprint-*' --no-pager

# 6. Versions runtime
php -v               # attendu : 8.3+
node -v && npm -v    # attendu : 20+ (pour Vite build sur serveur)
composer -V
psql --version       # attendu : 17.x — ADR-0020. `psql: command not found` est le cas NORMAL sur ce VPS : PostgreSQL n'y a jamais été posé, il l'est au §6
mysql --version      # pour mémoire : c'est le moteur de CheckPrint, plus celui de Takussan

# 7. Espace disque
df -h /var

PHP 8.4 requis — le serveur y est déjà (vérifié le 2026-08-12)

Le composer.lock du dépôt ne s'installe pas sur PHP 8.3 : 19 paquets verrouillés exigent 8.4 ou plus — 17 symfony/* en php >=8.4.1, plus lcobucci/clock et spatie/laravel-activitylog. Un composer install --no-dev sur un serveur en 8.3 échoue, et le déploiement s'arrête là.

Rien ne l'avait signalé parce que la CI tourne sur PHP 8.4 : la machine qui valide et la machine qui sert ne parlaient pas la même version, et c'est la seconde qui casse. Le dépôt déclare désormais "php": "^8.4" et fige la résolution par config.platform.php = 8.4.1, pour que composer refuse lui-même l'écart au lieu qu'on le découvre au déploiement.

Sur CE serveur, rien à faire : le déploiement de preview du 2026-06-20 a réussi alors que son composer.lock exigeait déjà php >=8.4.1 — et deploy.sh lance composer install --no-dev. Un install ne peut pas réussir sur une version que le lock exclut : le serveur est donc en 8.4 ou plus. Preview et production partagent la même machine.

Sur un serveur NEUF, ou encore en 8.3, dans cet ordre :

  1. sudo add-apt-repository ppa:ondrej/php && sudo apt update (Ubuntu ; sur Debian, dépôt Sury).
  2. Installer 8.4 avec toutes les extensions de la ligne ci-dessous — intl, gd, bcmath et redis manquaient à l'ancienne liste, et une extension absente ne dégrade pas une fonction : elle empêche l'application entière de démarrer.
  3. Recréer le pool FPM : sudo bash scripts/server-setup.sh (il détecte la version de PHP et réécrit /etc/takussan/php-version, que deploy.sh relit pour savoir quel service recharger).
  4. Vérifier : php -v, php -m | grep -E 'intl|gd|bcmath|redis', puis composer check-platform-reqs --no-dev dans la release courante.
  5. Ne désinstaller 8.3 qu'après un déploiement réussi sur 8.4.

Si une dépendance manque…

  • id deploy retourne "no such user" → CheckPrint n'a pas été déployé sur ce VPS. Crée-le : sudo adduser --disabled-password --gecos "" deploy && sudo usermod -aG www-data deploy.
  • PHP/Composer/Node absents → sudo apt update && sudo apt install -y php8.4-fpm php8.4-pgsql php8.4-mbstring php8.4-xml php8.4-curl php8.4-zip php8.4-intl php8.4-gd php8.4-bcmath php8.4-redis composer nodejs npm nginx certbot python3-certbot-nginx.
    ⚠ php8.4-pgsql et non php8.4-mysql (ADR-0020). Ce n'est pas une équivalence : sans pdo_pgsql, l'API ne se connecte pas du tout. Contrôle : php -m | grep pdo_pgsql.
    Depuis le 2026-08-21, tu n'as plus à y penser : composer.json déclare ext-pdo_pgsql, et deploy.sh lance composer check-platform-reqs avant le composer install. Un serveur sans le pilote fait donc échouer le déploiement au lieu de servir une application qui meurt à la première requête. Vérifié par ablation : une extension absente rend une sortie 2 et la liste la ligne missing.
  • PostgreSQL absent → voir le §6, qui le pose avec sa collation. Ne pas l'installer d'un simple apt install postgresql ici : la base doit être créée en --locale=C, et ça ne se rattrape pas après coup sans la recréer.

5Bootstrap serveur avec server-setup.sh

Pourquoi cette étape ? Cette étape installe sur ton VPS toute la plomberie dont Laravel a besoin : un user dédié deploy, les dossiers où les releases vont vivre, les pools PHP-FPM, les vhosts Nginx, les services systemd pour les queues, le cron pour le scheduler Laravel, les sudoers pour les reloads, et le logrotate. Un seul script — il fait preview ET prod en parallèle.

5.1 Lancer le script

Depuis ton poste local (le repo Takussan checkouté en local) :

bash — depuis ton poste local 
# 1. Copier le script sur le VPS
scp scripts/server-setup.sh admin@<IP_VPS>:/tmp/

# 2. Se connecter au VPS et l'exécuter en root
ssh admin@<IP_VPS>
sudo bash /tmp/server-setup.sh
rm /tmp/server-setup.sh

5.2 Ce que le script fait — et tu n'as donc pas à faire à la main

  • Crée le user deploy (s'il n'existe pas déjà) et l'ajoute à www-data.
  • Crée les dossiers /var/www/takussan/ et /var/www/takussan-preview/ avec leurs sous-dossiers releases/ et shared/storage/.
  • Pré-remplit ~deploy/.ssh/known_hosts avec les host keys GitHub (fingerprint ED25519 vérifié contre une valeur hardcodée pour éviter MITM).
  • Crée les deux pools PHP-FPM (takussan, 10 workers / takussan-preview, 5 workers) avec sockets dédiés.
  • Pin la version PHP détectée dans /etc/takussan/php-version (utilisé par deploy.sh pour reloader le bon FPM).
  • Crée les deux vhosts Nginx en HTTP (Certbot ajoutera le 443 ensuite) et valide avec nginx -t avant de reload.
  • Crée les deux services systemd takussan-queue et takussan-queue-preview.
  • Ajoute le cron Laravel scheduler pour les deux envs (schedule:run chaque minute).
  • Écrit /etc/sudoers.d/takussan-deploy (NOPASSWD reload php-fpm / nginx, start/restart queues) validé via visudo -c.
  • Écrit /etc/logrotate.d/takussan (rotation 14j sur les logs Laravel des deux envs).
  • Affiche en fin de run un validation summary avec PASS/FAIL pour chaque composant.

Le script est idempotent : tu peux le relancer autant de fois que tu veux. Il détecte ce qui est déjà en place et ne casse rien.

Si tu vois des FAIL…

  • FAIL php8.4-fpm active → sudo apt install php8.4-fpm puis relance le script.
  • FAIL nginx -t passes → un autre vhost a une erreur ; sudo nginx -t pour la voir.

Édition manuelle d'un pool PHP-FPM (pour retuner après coup)

Si tu veux changer pm.max_children ou la mémoire d'un pool sans relancer tout le script, édite le fichier directement (les chemins ci-dessous sont pour PHP 8.3 — adapte avec php -v) :

bash
# Pool preview (chemin) : /etc/php/8.3/fpm/pool.d/takussan-preview.conf
# Pool prod    (chemin) : /etc/php/8.3/fpm/pool.d/takussan.conf
sudo nano /etc/php/8.3/fpm/pool.d/takussan.conf

# Appliquer (gracieux, ne coupe pas les requêtes en cours) :
sudo systemctl reload php8.4-fpm

# Vérifier que les sockets sont là :
sudo ls -la /run/php/takussan.sock /run/php/takussan-preview.sock
Édition manuelle d'un vhost Nginx (pour customiser cache, rewrite, etc.)

Les vhosts sont à /etc/nginx/sites-available/api.takussan.com et /etc/nginx/sites-available/preview.api.takussan.com. Modèle complet du vhost preview :

nginx — /etc/nginx/sites-available/preview.api.takussan.com
server {
    listen 80;
    listen [::]:80;
    server_name preview.api.takussan.com;
    # Pour prod : server_name api.takussan.com; et adapter les chemins ci-dessous.

    root /var/www/takussan-preview/current/public;
    index index.php;
    client_max_body_size 25M;

    access_log /var/log/nginx/preview.api.takussan.com.access.log;
    error_log  /var/log/nginx/preview.api.takussan.com.error.log;

    location /storage/ {
        alias /var/www/takussan-preview/shared/storage/app/public/;
        expires 7d;
    }

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        include snippets/fastcgi-php.conf;
        fastcgi_pass unix:/run/php/takussan-preview.sock;
        # Pour prod : fastcgi_pass unix:/run/php/takussan.sock;
        fastcgi_param SCRIPT_FILENAME $document_root$fastcgi_script_name;
        fastcgi_read_timeout 60;
    }

    location ~ /\.(?!well-known) { deny all; }
}

Appliquer après édition :

bash
sudo nginx -t && sudo systemctl reload nginx

6PostgreSQL & Meilisearch — services VPS

Pourquoi cette étape ? Laravel a besoin d'une base pour stocker ses données. On crée deux bases isolées (preview et prod) avec deux rôles distincts. Comme ça si une migration casse la base preview, la prod est en sécurité.

Le moteur est PostgreSQL 17 depuis ADR-0020 (2026-08-21), sur tous les environnements, suite de tests comprise. Cette section prescrivait MySQL jusque-là ; la suivre aujourd'hui déploierait une API qui ne démarre pas.

Cette étape est manuelle, et elle le reste : server-setup.sh n'installe aucune base de données — ni MySQL hier, ni PostgreSQL aujourd'hui. Il configure PHP-FPM, nginx et les unités systemd, rien d'autre. Son propre commentaire le dit désormais.

Nom de la basetakussan_previewtakussan_prod
Rôle PostgreSQLtakussan_pretakussan_pro

6.1 Générer deux passwords forts

Toujours sur le VPS, génère deux passwords différents (un par environnement) :

bash — sur le VPS
# Password preview — copie-le dans un coin pour le §7
openssl rand -base64 24

# Password prod — différent du preview
openssl rand -base64 24

6.2 Créer les deux bases et les deux users

bash — sur le VPS
# Poser le serveur, s'il ne l'est pas déjà. `postgresql-17-pgvector` est installé
# MAINTENANT bien qu'AUCUNE table ne l'utilise : ADR-0020 §2 — l'extension doit être
# disponible partout dès le départ, sinon le motif se referme en silence le jour du
# chatbot (TCK-344), et l'ajouter à un serveur qui sert coûte davantage.
sudo apt update && sudo apt install -y postgresql-17 postgresql-17-pgvector php8.4-pgsql
sudo systemctl enable --now postgresql

sudo -u postgres psql <<'SQL'
-- ═══════ RÔLES ═══════
CREATE ROLE takussan_pre LOGIN PASSWORD 'PASSWORD_PREVIEW_DU_6_1';
CREATE ROLE takussan_pro LOGIN PASSWORD 'PASSWORD_PROD_DU_6_1';
SQL

# ═══════ BASES ═══════
# ⚠ `--locale=C` est la ligne la PLUS IMPORTANTE de cette étape, et elle ne se
# rattrape pas : une base créée avec la locale par défaut du serveur a une collation
# différente, et le SENS de six contraintes d'unicité sur texte en dépend
# (ADR-0020 §4.2). Une contrainte qui change de sens ne lève AUCUNE erreur — elle
# laisse passer un doublon, et ça se découvre dans les données des mois plus tard.
# `--template=template0` est obligatoire dès qu'on impose une locale.
# Ces bases se créent en CLI et non en SQL : `CREATE DATABASE … LOCALE` refuse de
# tourner dans le psql interactif ci-dessus si template1 a une autre locale.
sudo -u postgres createdb --owner=takussan_pre --encoding=UTF8 \
     --locale=C --template=template0 takussan_preview
sudo -u postgres createdb --owner=takussan_pro --encoding=UTF8 \
     --locale=C --template=template0 takussan_prod

Garde les deux passwords précieusement — tu vas les coller dans les secrets GitHub ENV_FILE et ENV_FILE_PREVIEW à la section suivante. Si tu les perds, régénère-les avec sudo -u postgres psql -c "ALTER ROLE takussan_pro PASSWORD '…';".

C'est exactement ce qui a coûté le déploiement du 2026-08-15 : deploy.yml est mort deux fois sur Access denied for user 'takussan_prod'@'localhost', et le journal ne disait pas de quel côté était l'écart — secret périmé, compte absent ou grant manquant se ressemblent tous les trois (ardoise D-04). 6.4 Meilisearch — moteur de recherche

Pourquoi cette étape ? La recherche plein-texte (biens, messages, documents) tourne sur Meilisearch via Laravel Scout. Comme PostgreSQL, c'est un service à installer manuellement — server-setup.sh ne le provisionne pas. Une seule instance sert preview et prod, les index étant isolés par SCOUT_PREFIX.

Installer le binaire (dépôt apt officiel), créer l'utilisateur système et les répertoires de données :

bash — sur le VPS
# Binaire Meilisearch via le dépôt apt officiel
echo "deb [trusted=yes] https://apt.fury.io/meilisearch/ /" | sudo tee /etc/apt/sources.list.d/meilisearch.list
sudo apt update && sudo apt install meilisearch

# Utilisateur système dédié + répertoires de données
sudo useradd -d /var/lib/meilisearch -s /bin/false -m -r meilisearch
sudo mkdir -p /var/lib/meilisearch/data /var/lib/meilisearch/dumps /var/lib/meilisearch/snapshots
sudo chown -R meilisearch:meilisearch /var/lib/meilisearch

Générer une master key et écrire la configuration /etc/meilisearch.toml :

bash — sur le VPS
# Master key — garde-la, elle ira dans les secrets ENV_FILE / ENV_FILE_PREVIEW (§7)
openssl rand -base64 24

sudo tee /etc/meilisearch.toml >/dev/null <<'TOML'

master_key   = "COLLE_LA_MASTER_KEY_ICI"
db_path      = "/var/lib/meilisearch/data"
dump_dir     = "/var/lib/meilisearch/dumps"
snapshot_dir = "/var/lib/meilisearch/snapshots"
http_addr    = "127.0.0.1:7700"
TOML
sudo chown meilisearch:meilisearch /etc/meilisearch.toml
sudo chmod 640 /etc/meilisearch.toml

Créer le service systemd, l'activer et vérifier la santé de l'instance :

bash — sur le VPS
sudo tee /etc/systemd/system/meilisearch.service >/dev/null <<'UNIT'
[Unit]
Description=Meilisearch
After=network.target

[Service]
User=meilisearch
Group=meilisearch
ExecStart=/usr/bin/meilisearch --config-file-path /etc/meilisearch.toml
Restart=on-failure

[Install]
WantedBy=multi-user.target
UNIT

sudo systemctl daemon-reload
sudo systemctl enable --now meilisearch
curl http://127.0.0.1:7700/health        # attendu : {"status":"available"}

Master key & index partagés. Reporte la master key dans les secrets ENV_FILE et ENV_FILE_PREVIEW (variable MEILISEARCH_KEY, §7). Une seule instance Meilisearch sert les deux environnements : le .env preview porte SCOUT_PREFIX=preview_ pour préfixer ses index et éviter toute collision avec la prod. Après le premier déploiement (étape 13), peupler les index une fois sur le serveur — php artisan scout:import "App\Models\Property" (puis Document et Message) ; ensuite le worker de queue les maintient à jour automatiquement.

8CORS & Sanctum cross-domain

Pourquoi cette étape ? Le front (sur takussan.com) et l'API (sur api.takussan.com) sont sur deux sous-domaines différents. Sans config CORS, le navigateur refuse les requêtes croisées. Sans cookies cross-subdomain, l'authentification Sanctum ne marche pas.

8.1 Configurer CORS côté Laravel

php — takussan-api/config/cors.php
return [
    'paths' => ['api/*', 'sanctum/csrf-cookie', 'login', 'logout', 'storage/*'],
    'allowed_methods' => ['*'],
    'allowed_origins' => [
        env('FRONTEND_URL', 'http://localhost:3000'),
    ],
    'allowed_origins_patterns' => [
        // Preview builds Vercel : takussan-<hash>.vercel.app
        '#^https://takussan-[a-z0-9-]+\.vercel\.app$#',
    ],
    'allowed_headers' => ['*'],
    'exposed_headers' => [],
    'max_age' => 0,
    'supports_credentials' => true,   // OBLIGATOIRE pour Sanctum cookies
];

8.2 Côté Next.js — toujours envoyer les cookies

typescript
// Toutes les requêtes authentifiées doivent inclure les cookies
fetch(`${process.env.NEXT_PUBLIC_API_URL}/api/...`, { credentials: 'include' });

// Avant un login Sanctum, demander le cookie CSRF
await fetch(`${process.env.NEXT_PUBLIC_API_URL}/sanctum/csrf-cookie`, {
  credentials: 'include',
});

Le point devant SESSION_DOMAIN est essentiel. .takussan.com couvre tous les sous-domaines (preview.takussan.com, preview.api.takussan.com, etc.). Sans le point, le cookie posé par l'API n'est pas lisible par le front. L'isolation entre envs se fait via SESSION_COOKIE distinct (cf. §7).

9SSH GitHub Deploy Key

Pourquoi cette étape ? Le script deploy.sh sur le VPS doit cloner le repo Takussan depuis GitHub à chaque déploiement. Il a donc besoin d'une clé SSH qui prouve à GitHub que le VPS est autorisé à lire le repo.

Une deploy key est une clé SSH liée à un seul repo GitHub (≠ d'une clé user qui peut accéder à tous tes repos). Read-only suffit pour un deploy.

9.1 Générer la clé sur le VPS, en tant que deploy

bash — sur le VPS
ssh admin@<IP_VPS>
sudo -iu deploy

# Générer une clé ed25519 dédiée Takussan, sans passphrase
ssh-keygen -t ed25519 -C "takussan-deploy-key" -f ~/.ssh/takussan_deploy -N ""

# Afficher la clé publique
cat ~/.ssh/takussan_deploy.pub

9.2 Ajouter la clé publique dans GitHub

  1. Copie la clé publique affichée (commence par ssh-ed25519 ...).
  2. Va dans GitHub → repo takussan → Settings → Deploy keys → Add deploy key.
  3. Titre : Contabo deploy. Colle la clé.
  4. Ne coche PAS "Allow write access" — le deploy a juste besoin de lire.
  5. Clique Add key.

9.3 Configurer l'alias SSH côté VPS

On crée un alias github.com-takussan qui force SSH à utiliser cette clé spécifique pour ce repo. Sans ça, SSH essaierait toutes tes clés et pourrait s'identifier sur le mauvais repo.

bash — toujours en tant que deploy
cat >> ~/.ssh/config <<'CFG'
Host github.com-takussan
    HostName github.com
    User git
    IdentityFile ~/.ssh/takussan_deploy
    IdentitiesOnly yes
CFG
chmod 600 ~/.ssh/config

# Tester
ssh -T github.com-takussan
# Attendu : "Hi <owner>/takussan! You've successfully authenticated, but GitHub does not provide shell access."

Si ssh -T affiche…

  • Hi <owner>/<autre-repo>! → la clé est enregistrée sur le mauvais repo dans GitHub. GitHub n'autorise une même clé qu'à un seul repo en deploy key. Génère une nouvelle clé dédiée Takussan (étape 9.1).
  • Permission denied (publickey) → la clé publique n'a pas été ajoutée au repo Takussan. Reprends l'étape 9.2.
  • Could not resolve hostname github.com-takussan → le bloc Host github.com-takussan n'est pas dans ~/.ssh/config. Vérifie avec cat ~/.ssh/config.

Tu utiliseras cet alias dans le REPO_URL du secret GitHub (§10) : git@github.com-takussan:<owner>/takussan.git.

9.4 SSH key pour GitHub Actions ↔ VPS

GitHub Actions doit pouvoir se connecter au VPS pour y déclencher deploy.sh. Le secret CONTABO_SSH_KEY contient cette clé privée. Si CheckPrint est déjà déployé sur ce VPS, sa clé existe déjà — tu peux la réutiliser telle quelle, c'est le même user deploy.

11SSL Let's Encrypt

Pourquoi cette étape ? Pour servir l'API en HTTPS. Sans certificat, le navigateur bloque les cookies cross-domain (cookies "Secure" obligatoires en cross-site), et Sanctum ne marche pas.

Prérequis : les DNS du §2 doivent être propagés (les A records api et preview.api doivent résoudre vers l'IP du VPS). Certbot a besoin de joindre /.well-known/acme-challenge/ sur le domaine pour valider que tu en es propriétaire.

bash — sur le VPS
# Certificat preview
sudo certbot --nginx \
  -d preview.api.takussan.com \
  --redirect --agree-tos -m mouhamadoulaminethiam97@gmail.com --no-eff-email

# Certificat prod
sudo certbot --nginx \
  -d api.takussan.com \
  --redirect --agree-tos -m mouhamadoulaminethiam97@gmail.com --no-eff-email

# Tester le renouvellement automatique (ne renouvelle pas vraiment, juste un dry-run)
sudo certbot renew --dry-run

Certbot modifie les vhosts Nginx pour ajouter le bloc listen 443 ssl + un 301 redirect HTTP → HTTPS. Pas besoin d'y toucher après.

Le renouvellement automatique est installé en cron par le paquet certbot (/etc/cron.d/certbot). Tu n'as plus rien à faire — les certs se renouvellent tout seuls 30 jours avant expiration. Le --dry-run ci-dessus vérifie juste que le mécanisme marche.

Si certbot timeout sur l'API…

  • Vérifie que le record A correspondant dans Cloudflare est bien en DNS only (gris) et propagé (dig +short api.takussan.com).
  • Si tu utilises Cloudflare en Proxied (orange), Certbot HTTP-01 fonctionne quand même tant que CF n'intercepte pas /.well-known/acme-challenge/. Alternative robuste : certbot --dns-cloudflare avec un API token CF.

12deploy.sh & workflows GitHub Actions

Pourquoi cette étape ? C'est le cœur du système. deploy.sh orchestre chaque déploiement (clone, build, migrate, swap atomique, healthcheck). Les workflows GitHub Actions le déclenchent automatiquement à chaque push sur preview ou master.

12.1 Comment deploy.sh fonctionne

Le script est versionné à scripts/deploy.sh dans le repo et poussé sur le VPS par GitHub Actions à chaque run (la version sur le VPS est donc toujours celle du commit en cours). Étapes :

  1. Pré-flight : écrit le .env depuis le secret GH, valide qu'APP_KEY=base64:... est bien présent (FATAL sinon).
  2. Clone de la branche dans releases/<timestamp>/.
  3. Symlinks du .env et de storage/ partagés (depuis shared/) dans la nouvelle release.
  4. Composer install + npm ci + npm run build + rm node_modules (économise ~500 MB par release).
  5. Migrations (php artisan migrate --force).
  6. Caches (config, route, view).
  7. Swap atomique : current pointe vers la nouvelle release.
  8. Reload PHP-FPM pour vider opcache (sinon le code reste le précédent !).
  9. Healthcheck : curl 127.0.0.1/up ; non-200 → rollback automatique.
  10. Restart queue workers.
  11. Cleanup : garde les 5 dernières releases.

Si une étape échoue (composer, migrate, healthcheck…), le trap rollback ERR restaure le symlink current sur la release précédente et supprime la release fautive. Aucune intervention manuelle requise pour les ratés courants.

14Rollback

Pourquoi cette étape ? Si un deploy casse la prod, tu dois pouvoir revenir à l'ancienne version immédiatement. Il y a deux niveaux : automatique (intégré à deploy.sh) et manuel (si tu détectes le problème après coup).

⚠️ Ce que le rollback NE PEUT PAS annuler : les migrations (mesuré le 2026-08-12)

Les deux niveaux décrits ci-dessous restaurent le code — le symlink current repointe sur la release précédente. Ils ne touchent pas au schéma : deploy.sh ne joue jamais migrate:rollback, et c'est délibéré. Une base revenue en arrière pendant qu'un ancien code tourne dessus est plus dangereuse qu'un schéma en avance.

Et une migration est irréversible par construction. 2026_05_18_120000_drop_spatie_permission_tables — le cutover RBAC de TCK-278 — lève une exception dans son down() : reconstituer des rôles historiques depuis un seeder n'aurait restauré qu'une approximation, ce qui est pire qu'un refus. Il n'existe donc aucune marche arrière de schéma au-delà de cette migration, seulement une restauration de dump.

Conséquence opérationnelle, à tenir avant d'en avoir besoin :

  1. Dump avant chaque déploiement qui porte une migration. C'est la seule marche arrière réelle : sudo -u postgres pg_dump --format=custom takussan_prod > /var/backups/takussan/pre-deploy-$(date +%F-%H%M).dump
    ⚠ pg_dump et non mysqldump (ADR-0020). --format=custom plutôt que du SQL brut : c'est le seul format que pg_restore sait restaurer partiellement — une table, un schéma — au lieu de tout ou rien. Restauration : sudo -u postgres pg_restore --clean --if-exists -d takussan_prod <fichier>.
  2. Vérifier que le dump est non vide et relisible avant de lancer le deploy — un dump qu'on n'a jamais relu n'est pas une sauvegarde.
  3. Le job migrations-pgsql de la CI rejoue des migrations aller ET retour avant le merge. Il a trouvé un down() cassé sur trois tables à sa première exécution : la suite de tests n'exécute aucun down().
    ⚠ Il a changé de raison d'être le 2026-08-21, et il en couvre moins qu'il n'y paraît. Il s'appelait migrations-mysql et gardait deux choses : que le DDL passe sur le moteur réel, et que les down() tiennent. La première a disparu — depuis ADR-0020 la suite de tests tourne sur le moteur de la production, donc le DDL y est déjà éprouvé. Il ne reste que les down(), et seulement 15 sur 135 : ceux au-dessus de la borne TCK-278, dont le down() est délibérément irréversible. Ne pas lire ce job comme « les down() sont couverts » — il imprime son propre compte à chaque exécution.

14.1 Rollback automatique pendant le deploy

Le trap rollback ERR dans deploy.sh restaure le symlink current sur la release précédente si une étape post-clone échoue (composer, migrate, healthcheck non-200, etc.). Tu n'as rien à faire.

14.2 Rollback manuel (après coup)

Si un deploy est passé sans erreur mais que tu réalises qu'il a introduit un bug, tu peux pointer current sur une release antérieure :

bash — sur le VPS
ssh deploy@<IP_VPS>

# Adapter le chemin selon l'env : /var/www/takussan-preview/ ou /var/www/takussan/
cd /var/www/takussan/releases
ls -1t                                    # lister les releases par date décroissante

# Pointer current vers la release précédente
ln -sfn /var/www/takussan/releases/<ID_PRECEDENT>/takussan-api \
       /var/www/takussan/current

# Reload PHP-FPM pour purger opcache
sudo -n /bin/systemctl reload php$(cat /etc/takussan/php-version)-fpm

# Signaler la queue pour qu'elle reload
cd /var/www/takussan/current && php artisan queue:restart

14.3 Rollback front (Vercel)

Pour le front : dashboard Vercel → Deployments → trouve le deploy précédent stable → menu ··· → Promote.

Attention DB : le rollback restaure le code mais pas le schéma DB. Si la release fautive a tourné migrate --force, les tables/colonnes ajoutées sont toujours là. Écris toujours des migrations rétrocompatibles (ajouter des colonnes nullable, jamais drop sans 2 deploys séparés).

15Dépannage

Erreurs classiques rencontrées en première mise en place. Cherche celle qui ressemble à ton symptôme.

CORS error côté Next.js
  • "No 'Access-Control-Allow-Origin' header" → FRONTEND_URL dans le secret ENV_FILE_PREVIEW ne match pas l'origin. Corrige et redéploie.
  • "…Access-Control-Allow-Credentials is not 'true'" → supports_credentials => true dans config/cors.php. Le prochain deploy re-cache automatiquement avec php artisan config:cache.
Login passe mais requêtes suivantes 401
  • credentials: 'include' oublié côté Next.
  • SESSION_DOMAIN sans point devant.
  • SESSION_SAME_SITE=strict au lieu de lax.
  • HTTPS manquant d'un côté (l'un en HTTPS, l'autre en HTTP).
deploy.sh : "Permission denied (publickey)" lors du git clone
