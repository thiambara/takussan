# TCK-2389 — « Publier pour lui » : plan d'implémentation

> **Pour les agents :** sous-compétence `superpowers:subagent-driven-development`. Une tâche à la
> fois, cases `- [ ]`. Le ticket est le contrat :
> [`TCK-2389`](../backlog/tickets/TCK-2389-radar-publier-pour-l-annonceur.md) — lire sa section
> « Décisions du porteur (2026-10-29) ». Spec : `features.md` §2.12, `models-spec.md` §88, §109
> (PR #1580). Décisions : [ADR-0077](../adr/0077-le-radar.md) §6, §8, §11 ;
> [ADR-0033](../adr/0033-le-telephone-verifie-est-un-identifiant-de-connexion.md) §3 (amendement du
> 2026-10-29) ; ADR-0054 (empreintes) ; ADR-0072 (idempotence) ; ADR-0029 (disques).

**But :** le super-admin publie en un geste les annonces qu'un annonceur a acceptées : un compte
sans mot de passe, un espace `individual`, un bien publié par annonce avec ses photos, le numéro de
l'annonceur en contact ; l'annonceur l'active par un code SMS.

**Architecture :** trois briques côté API, appelées dans cet ordre. (1) La **réserve de photos**
d'une annonce se remplit après l'accord confirmé (job réseau) ou à la main ; (2)
`AdvertiserProvisioner` crée le compte et l'espace (`HostIndividualOnboardingService::autoOnboard`) ;
(3) `RadarPublisher` juge les accords, puis crée en une transaction compte, espace, biens, adresses,
contacts, copies de photos, et marque les annonces `published`. Aucun appel réseau dans `publish`.
Le front ajoute une page de publication par annonceur.

**Pile :** Laravel 13 / PHP 8.4 / PostgreSQL 17 ; spatie/laravel-medialibrary ; Intervention Image
(GD) ; Next.js 16 / React 19 / TanStack Query / next-intl.

## Contraintes globales

- **Aucune suite entière en local**, ni agent ni session : tests ciblés (`php artisan test
  <fichiers>`, `npx vitest run <fichiers>`), la CI joue les suites sur la PR. Ne jamais utiliser
  `php bin/impacted-tests.php` sans `--connus` (le défaut escalade en suite entière sur `config/`
  ou une migration).
- **Ne jamais lire ni afficher `takussan-api/.env`** (clé réelle) ; aucun test n'appelle un modèle
  ni le réseau (`Http::fake`, faux `HostResolver` comme `RadarUrlFetcherTest`).
- PostgreSQL : pas de `try/catch` d'une erreur SQL dans une transaction ; verrou sur la ligne parent
  (`lockForUpdate()->firstOrFail()`), jamais sur un agrégat ; ordre des verrous du Radar :
  **annonces → annonceur → message → réponse** (`AdvertiserClaim`).
- Erreurs métier : `abort_code(422|409|403, 'radar.<…>', [contexte])`, codes stables, jamais de
  prose ; le front possède le texte (`fr`, `en` ; `wo` = copie du français, wolof en pause).
- Toute validation dans un `FormRequest` (`BaseFormRequest`, `authorize()` explicite) ; toute
  réponse par `$this->json(...)` ; ressources étendant `BaseResource` ; dates par `iso()`.
- Médias : `radar_photos` sur le disque **par défaut (privé)**, déclaré dans
  `tests/Feature/Media/MediaDiskCollectionsTest.php` ; jamais `getPath()` (lire par
  `Storage::disk($media->disk)`, ou `PrivateMediaAccess`).
- Les jobs sont mis en file après commit (`after_commit` des connexions) ; un écouteur neuf ne
  s'inscrit nulle part (découverte automatique).
- `./vendor/bin/pint` avant chaque commit ; commits en français, préfixe conventionnel,
  `(TCK-2389)`, pied `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Pas de `git stash`.
- Front : `npm run lint`, `npx tsc --noEmit`, tous les `npm run check:*` ; une route admin neuve à
  paramètre a sa ligne réelle dans `tests/Feature/Admin/NamespaceAccessGuardTest.php` ; un
