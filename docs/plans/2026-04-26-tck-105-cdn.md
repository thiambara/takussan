# TCK-105 — CDN + webp/avif (plan d'implémentation)

## Contexte

Les médias (photos de biens, avatars, documents) sont aujourd'hui servis directement depuis le disque Spatie via `Media::getUrl()` (ex. `PropertyResource::64-72`, `MediaResource::conversionUrl`). Cela coûte en bande passante et latence pour des visiteurs distants, et expose des URLs publiques permanentes pour des collections sensibles (baux, documents contractuels).

**TCK-105** intercale une couche CDN **transparente** entre Spatie et les consommateurs, en réutilisant les conversions et le storage existants (TCK-016 + TCK-050, tous deux `done`). Aucune migration, aucun breaking change frontend : on remplace simplement le `url_generator` de Spatie. La sortie ajoute aussi le support des URLs signées TTL ≤ 5 min, l'invalidation de cache lors d'un replace/delete, et un fallback automatique sur le storage si le CDN tombe.

Choix de scope confirmés avec l'utilisateur :
- **Drivers** : Bunny complet (URL transform + signing + purge), Cloudflare en stub (lance `RuntimeException` sur `signUrl/purge`) — bascule future sans refactor du resolver.
- **Conversions** : on garde les noms existants (`thumbnail` 150×150, `preview` 400×400, `full` 1200×auto) ; le wording `thumb/card/web/original` du ticket est traité comme indicatif.

## Architecture

```
PropertyResource ─┐
MediaResource    ─┼─► Spatie Media::getUrl()  ──► CdnUrlGenerator (extends DefaultUrlGenerator)
DocumentResource ─┘                                       │
                                                          ▼
                                                   MediaUrlResolver
                                                   ├── circuit breaker (CdnHealthGuard)  ── fallback storage URL
                                                   ├── secure collections check          ── signUrl()
                                                   └── default                           ── transformUrl()
                                                          │
                                                          ▼
                                                  CdnProviderContract  ──► BunnyCdnDriver  (full)
                                                                       └─► CloudflareCdnDriver (stub)

Media::deleted/updated  ──► MediaCdnObserver  ──► PurgeCdnCacheJob (queued) ──► CdnProviderContract::purge()
```

## Détails d'implémentation clés

### CdnProviderContract
```
public function transformUrl(string $sourcePath, ?string $conversion = null, array $hints = []): string;
public function signUrl(string $sourcePath, ?string $conversion = null, int $ttlSeconds = 300, array $hints = []): string;
public function purge(array $urls): bool;
public function healthCheck(): bool;
```
`$hints` porte le contexte de format (`accept` header) et de viewport pour le format chain négocié côté CDN. Le contrat reste agnostique du provider.

### BunnyCdnDriver — signing
HMAC-SHA256 sur `signing_key . path . expiry` puis base64url, ajouté en query string `?token=…&expires=…` (Token Authentication standard Bunny). Tests sur vecteur connu pour stabilité.

### MediaUrlResolver — décision
1. `config('cdn.enabled') === false` → URL storage (`parent::getUrl()` reçue par injection callable).
2. `CdnHealthGuard::isOpen()` → URL storage + `Log::warning('cdn.fallback_open_breaker', context)`.
3. `in_array($media->collection_name, config('cdn.secure_collections'))` → `signUrl()`.
4. Sinon → `transformUrl()`.
Toute exception du driver → fallback storage + log + incrément du compteur `CdnHealthGuard`.

### CdnUrlGenerator (Spatie)
Spatie résout le générateur via `config('media-library.url_generator')`. On `extends DefaultUrlGenerator` pour conserver le comportement complet (signed URLs S3, conversions paths…). On override uniquement `getUrl()` et `getTemporaryUrl()`. La résolution de `MediaUrlResolver` se fait via `app(MediaUrlResolver::class)` au moment de l'appel (pas dans le constructeur — Spatie instancie le générateur via `make()` avec un Media, et la rétention d'état doit rester minimale).

### PurgeCdnCacheJob — pourquoi snapshot d'URLs et pas SerializesModels
Au moment où le job s'exécute, `Media` est supprimé (`deleted` event). Restaurer le modèle via `SerializesModels` lèvera `ModelNotFoundException`. On capture les URLs cibles (toutes conversions + original) **dans l'observer**, on les passe au constructeur du job, et le job appelle simplement `purge($urls)`.

### Pourquoi pas d'`Integration` model (vs SMS/Payments)
Le ticket spécifie explicitement des ENV (`CDN_PROVIDER`, `CDN_BASE_URL`, `CDN_SIGNING_KEY`, `CDN_PULL_ZONE`). Pas de UI tenant-scoped pour le CDN ; c'est une infra mono-instance par environnement. On reste sur `config/cdn.php` + ENV — aligné avec le ticket et plus simple.

### Health endpoint
`GET /api/health` n'existe pas — on l'ajoute localement (le ticket le prévoit). Public (pas de middleware auth) ; pas de PII ; chaque check a un timeout court pour éviter qu'une probe ne stalle la route. Réponse : `200` toujours, le détail sert au monitoring.
